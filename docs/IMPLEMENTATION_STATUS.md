> **What this is:** A live rollup of *build state* — what exists in code today, on which subsystem branch, and what is blocking it. One row per subsystem, not per task.
>
> **What this is not:** Not architecture (see `ADR_INDEX.md` → `THREAT_ENGINE_SPEC.md` → `EVENT_CONTRACTS.md` → `DATABASE_SCHEMA.md` → `DEEPSTREAM_PIPELINE_SPEC.md` → `FRONTEND_BACKEND_CONTRACTS.md` → `AGENTS.md`, per `CLAUDE.md`'s priority order). >
> **When to update:** Any time a subsystem's status, branch, or blocker changes — in the same PR/commit that causes the change, not on a schedule. Stale rows are worse than missing rows.
>
> **Who updates it:** Whoever changes the state — human or AI assistant.
>
> **Recommended read order when starting work in this repo:**
> `CLAUDE.md` → `PROJECT_CONTEXT.md` → `ADR_INDEX.md` → `TASKS.md` (root) → `docs/IMPLEMENTATION_ROADMAP.md` → **this file** → subsystem documentation / code.

## Architecture Contract

- This document tracks **implementation state only** — what is built, in progress, or blocked.
- It is **not** an architecture document and carries no authority over design decisions.
- It must **never** be edited to reflect, justify, or work around a change to architecture — architecture changes belong in an ADR (`ADR_INDEX.md`) per `CLAUDE.md`'s priority order.
- If implementation work conflicts with an architecture document, **implementation stops**. Do not resolve the conflict by editing the architecture doc or by proceeding around it — raise it for clarification (new ADR or human decision) first.

## Source of Truth

This document reflects the **operational implementation state** as last recorded by whoever updated it — it is a report, not a ledger. If it temporarily disagrees with the actual source code (a merged PR that hasn't updated a row yet, a rollback, a branch that moved faster than the doc), **the source code is authoritative** until this document is corrected. When you find a disagreement, fix the row — don't act on the stale status and don't treat the code as wrong because this file says otherwise.

## Implementation Notes

Running log of build-time findings that future contributors (human or AI) need but that don't belong in an ADR or spec. Newest first. Keep entries short. Move anything that becomes a durable architecture decision into an ADR instead of leaving it here.

- 2026-07-23 — **`nvstreammux` never reaches PLAYING with fewer active sources than `batch-size` unless `batched-push-timeout` is set.** Discovered during RM-11.SIV's real-hardware verification: a standalone harness driving the real `DeepStreamPipeline` sat at `frames_processed=0` for 3+ minutes with zero bus errors and no obvious cause. Isolating pipeline construction alone (no async orchestration) and polling `pipeline.get_state(0)` directly showed it stuck at `PAUSED, pending=PLAYING` indefinitely. Setting `batched-push-timeout` on the already-built element at runtime (bypassing `builder.py` entirely, as a diagnostic) fixed it in under 5 seconds — confirming the missing property, not something else, as the cause. This had been present since RM-11 Phase 0 (`streammux_batch_size` defaults to 20) but apparently never manifested in RM-11 Phase 1/2's own hardware verifications — worth remembering that a working multi-frame pipeline run does not by itself prove every source-count/batch-size combination works; single-camera-vs-batch-size-20 is exactly the SIV case that finally exercised it. Fixed with `DeepStreamSettings.streammux_batched_push_timeout_us` (default 40000µs).
- 2026-07-23 — **A component fed by a derived/computed value (not a direct event hook) is a Unified-Heartbeat trap.** RM-11.SIV's `Watchdog` initially computed `pipeline_fps` liveness by tracking `PerformanceInstrumentation.snapshot().frames_processed` across successive `check_once()` calls, entirely inside `Watchdog`'s own instance state — never writing anything back to the shared `HeartbeatRegistry`. This passed every SDK-free unit test (the tests only ever asked `Watchdog` itself), but on real hardware the `Dashboard` (which only ever reads `HeartbeatRegistry` directly, correctly, per the design) showed `pipeline_fps` permanently stalled while `Watchdog.check_once()` simultaneously reported it healthy — two consumers of "the same" data, silently disagreeing. Fixed by finding the actual per-frame event this was trying to approximate (`RuntimeAdapter.on_frame_observation`, which already existed) and beating the registry directly from there instead. Lesson for any future "derive component X's liveness from existing numeric state" temptation in this codebase: if two things are supposed to be reading one source of truth, only one of them should ever be *computing* anything — the other must be a pure read.
- 2026-07-22 — **RM-11 reference-environment detection and verification**, performed by direct inspection (not assumption) per an explicit repository-environment-update instruction. Detected: DeepStream SDK 7.0.0 (`/opt/nvidia/deepstream/deepstream-7.0/version`), GStreamer 1.20.3 (`gst-inspect-1.0 --version`), CUDA 12.2 / driver 535.288.01 (`nvidia-smi`, `nvcc --version`), TensorRT 8.6.1 (`libnvinfer` 8.6.1.6 via dpkg), GPU NVIDIA GeForce RTX 3060 12GB, `nvstreammux`/`nvinfer` GStreamer plugins present (`gst-inspect-1.0`). Two Python interpreters exist on this machine: `/usr/bin/python3` (system, 3.10 — the one DeepStream 7.0/Ubuntu 22.04's `gi`/`Gst`/TensorRT-python bindings are actually installed against) and `/home/dev/miniconda3/bin/python3` (3.13 — what this repo's own `pytest`/`ruff`/`black`/`mypy` run under, per earlier RM-11 Phase 0 work). Neither had `pyds` (DeepStream's Python metadata bindings) installed; `gi`/`PyGObject` and TensorRT's Python module were present only under the system interpreter. Installed `pyds` 1.1.11 user-locally (`pip install --user`) under the system Python from NVIDIA-AI-IOT's `deepstream_python_apps` v1.1.11 release wheel (the last release with a `py3-none` x86_64 wheel; newer releases are `cp312`-only, which doesn't match this machine's system Python 3.10) — this repo has no dependency on `pyds` under its own `requirements*.txt`/test suite; it is a machine-level DeepStream SDK companion, not a repo Python dependency. Built and ran a throwaway smoke-test script (`/tmp/rm11_env_verify.py`, not committed — scratch, reproducible from this note) under the system Python: `uridecodebin` (a DeepStream sample video) → `nvstreammux` → `nvinfer` (DeepStream's own stock `resnet18_trafficcamnet` sample detector, deliberately **not** the project's own weapon/uniform models — RM-11 design review Decision C keeps model readiness untouched) → a pad probe parsing `NvDsBatchMeta` via `pyds` → the real, unmodified Phase 0 `AsyncBridge.schedule()` → the real `RuntimeAdapter.on_pipeline_error()` → the real `InProcessEventBus.publish()`, all imported directly from `apps/deepstream/app`/`shared/events`. - 2026-07-20 — Postgres's `func.now()` (used for `server_default` on `created_at` columns, `apps/api/app/models/base.py`) returns *transaction start time*, not per-statement time -- two inserts in the same uncommitted transaction get an identical `created_at`. This broke a test relying on "latest by `created_at` wins" ordering (RM-05's `get_latest_for_camera()`) until the test was fixed to `commit()` between the two inserts, simulating the separate requests/transactions real usage would have. Not an implementation bug -- watch for it in any future test that creates >1 row of the same append-only-history table without committing in between and then asserts on `created_at` ordering.
- 2026-07-20 — mypy hit a hard error ("Duplicate module named conftest") once a second file literally named `conftest.py` appeared under `tests/` without an enclosing `__init__.py` chain (`tests/services/incident_service/conftest.py` vs. root `conftest.py`) — unlike advisory findings, this stops mypy from analyzing anything at all. - 2026-07-20 — Alembic's `autogenerate` does not emit ENUM type drops in `downgrade()` for Postgres `sa.Enum` columns (it drops the tables but leaves the `CREATE TYPE`-created types behind), which breaks re-`upgrade()` after a `downgrade()` with "type already exists". Watch for this on any future migration that adds a new Postgres-native enum column.
